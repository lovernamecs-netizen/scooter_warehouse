## 남은 한계와 후속 기준

- 부품 원장은 아직 단일 JSON이다. 읽을 때 전체 파싱, 저장할 때 전체 쓰기가 남는다. 수백만 건까지 일정 성능을 보장하지 않는다. 월간 응답이 반복적으로 2~3초를 넘거나 업무 저장 지연이 늘면 원장 행 분리와 기간 인덱스 이관을 별도 설계한다. 이관 전후 마감 서명·Snapshot·감사 이력을 대조해야 한다.
- 전체 차량 상태 응답과 차량 재고 재구성은 여전히 누적 데이터에 비례하는 부분이 있다. 향후 서버 측 검색·페이지 조회로 전환할 때 과거 VIN 검색 범위를 보존해야 한다.
- 사진 상태 조회와 전체 백업·보관 검증은 사진 총량에 비례한다. 증분 백업은 이번 변경에 포함하지 않았다. 실제 사진 총량·디스크 속도에서 백업 소요 시간과 여유 공간을 측정해야 한다.
- 같은 PC의 백업만으로 PC/디스크 전체 고장에 대비할 수 없다. 외장 또는 별도 장치에 검증된 복사본을 두고 주기적으로 **새 폴더** 복구 연습을 해야 한다. 고객정보 암호화 키와 암호화된 복구 키 백업은 기존 별도 복구 절차에 따라 보관한다. DB/사진 ZIP만으로 키 복구를 보장하지 않는다.
- 다수 사용자 실사용 동시 부하, 수년간 연속 가동, 실제 대용량 사진 디스크 장애, 갤럭시 실기기는 미검증이다. APK 변경/빌드는 없다.

## 운영 반영 및 복구 절차

1. 운영 HEAD와 작업 트리가 기준과 같은지 확인한다. 다른 변경이 있으면 통째 복사하지 않고 Git 차이를 검토한다.
2. 업무 쓰기를 중지한 뒤 DB를 SQLite backup API로 저장하고 integrity_check를 확인한다. 운영 사진·환경·큐 및 암호화 복구 자료를 기존 절차대로 별도 보존한다. DB/WAL/SHM을 각각 덮어쓰지 않는다.
3. 검증된 이 커밋을 운영 브랜치에 fast-forward로 적용한다. 최초 시작 시 인덱스 생성 시간과 디스크 여유를 확인한다.
4. 서버 재시작 후 인증, 재고·출고·일 마감 조회, 백업 상태를 읽기 위주로 확인한다. 반영 전후 업무 행과 사진의 보존 여부를 비교한다.
5. 코드 문제가 있으면 변경을 되돌리는 새 Git 커밋으로 복구한다. 추가 인덱스는 업무 데이터가 아니며 이전 코드와 공존할 수 있다. 배포 후 새로 입력된 업무를 잃을 수 있으므로 과거 DB 백업을 자동으로 덮어쓰지 않는다. DB 복구는 별도 폴더 검증 및 이후 업무 보존 계획을 거친다.

이 문서 작성 시 운영은 기준 커밋 상태이며, 이번 변경의 운영 배포와 GitHub push는 실행하지 않았다.
