운영 DB로 테스트하지 않았으며 별도 합성 DB·사진·암호화 키를 사용했다.

## 변경과 보존 범위
- server/app.py, web/app.js: 5초 주기 전체 상태 조회를 작은 인증된 버전 조회로 대체. revision·한국 날짜·계정 권한 변경 시 전체 조회하며, 변경이 없어도 60초마다 전체 조회한다. 수동 새로고침/명령 후 조회는 기존 동작을 유지한다. 공유 사용자 캐시 없음.
- server/domain.py: 요청 안에서 차량 관련 마스터/입고 회차/활성 주문/장착품을 묶어 조회. 기존 단건 DTO와 동등성 검사. 장착품 정정 권한 및 중고차 상세 검증은 기존 함수 유지.
- server/photo_backup.py: 일관된 DB 스냅샷과 파일 목록을 먼저 고정하고, 압축·검증은 DB 쓰기 잠금 밖에서 실행. 파일은 1MB씩 읽고 원본 SHA-256 및 전체 백업 검증을 유지한다. 실패 시 기존 긴급 백업 경로 유지.
- web/parts.js: 늦게 도착한 이전 날짜 응답 폐기. web/app.js: 차량 재고 날짜 변경 후 사용자가 펼친 패널 상태 유지.
- server/customer_privacy.py, web/customers.js: 업체/개인 분류를 페이지 제한 전에 적용하고 다음 검색 결과를 스크롤로 추가 조회. 기존 중복 방지와 접근 권한 유지.
- web/purchases.js: 사용되지 않는 클라이언트 중복 필터/달력 계산 제거.
- web/product-theme.css: 모든 공통 캘린더 날짜 숫자만 좌측 상단·font-weight 400으로 변경. 글씨 크기, 토/일/공휴일 색상, 내용 정렬, 메뉴 구성 유지.
- web/index.html, web/sw.js, 변경 모듈 import: 배포 캐시 버전 갱신.
- 테스트는 현재 권한 정책·접힌 메뉴·월 확정 UI에 맞춰 경로를 정정했다. 제품 권한을 테스트에 맞춰 완화하지 않았다.

DB 스키마 변경, 데이터 일괄 수정, 주문·출고·실사 재계산 없음. 사진/키/환경 파일 교체 없음. Android 기본 카메라 연결 및 취소된 등록 OCR 상태 유지. GitHub push 없음.

## 성능 측정의 범위
- 합성 차량 1,001대(활성 주문 1건)의 전체 상태 조회 SQL 25회. 동일 결과를 단건 DTO 경로와 비교했다. 이전 감사의 1,000대 단순 차량 측정은 5,014회였으나 완전히 같은 데이터셋은 아니므로 절대 처리시간 비교로 쓰지 않는다.
- 동일 합성 데이터 응답 본문: 전체 상태 651,660바이트, 버전 확인 475바이트. 이는 상태 확인 1회 비교이며 전체 앱 통신량 절감률을 뜻하지 않는다.
- 브라우저 11초 관찰에서 변경 없는 상태의 전체 /api/state 요청 0회, /api/state/version 요청 2회 이상 확인.
- 업무 알림의 기존 5초 조회는 유지한다. 60초 주기 전체 확인도 있으므로 통신량이 0이 되지는 않는다.
- 실제 PC 전체 네트워크 Mbps, 외부 회선 지연, 장시간 다중 사용자 부하, 실제 갤럭시 기기는 미검증이다.
- 초기 전체 상태 응답 크기는 차량 수에 비례한다. 장착품 정정 권한/중고 상세의 추가 조회도 남아 있다. 향후 훨씬 큰 데이터에서 초기 로딩 페이지 분리를 검토할 수 있으나 이번에는 기존 UI/기능 계약을 보존했다.

## 배포 및 복구
1. 운영 Git 청결/83b33bd 기준, 실행 서버 identity와 DB 경로를 확인한다.
2. 해당 서버만 중지하고 SQLite backup API로 일관된 DB 복사본을 생성한다. integrity_check와 사진 전체 복사·해시 검증을 수행한다. 백업은 Git 밖 deployment-recovery/stability-network-*에 둔다.
3. 검증 커밋으로 운영 브랜치를 --ff-only 병합한다. 업무 행·사진·환경 파일 보존을 확인하고 기존 실행 방식으로 서버를 재시작한다.
4. 서버 identity, HTTP 응답과 배포 파일 해시를 확인한다. 배포 결과 JSON은 복구 폴더에 보관한다.
5. 코드 복구는 새 업무 데이터를 보존하면서 안정화 커밋을 git revert하는 방식으로 수행한다. reset --hard나 이전 DB 덮어쓰기를 하지 않는다. DB 복구가 필요한 별도 사고라면 서버를 중지하고 현재 DB/WAL/SHM 및 사진을 추가 보존한 다음, 백업을 새 폴더에 복구·검증하여 전환한다. 백업 이후 업무를 자동으로 버리지 않는다.

이번 변경은 웹·서버 패치이며 새 APK 빌드 대상이 아니다.
