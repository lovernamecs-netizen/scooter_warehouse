# 고객정보·출고·승계 기반 설계 및 검증

기준 운영 커밋: 4a9ea36. 개발 브랜치: codex/customer-access-foundation-20261028.
운영 DB/사진/계정에는 적용하지 않았다. 개발은 Git worktree, 검증은 테스트 DB와 합성 자료로 수행했다.

## 구현 범위
- 지도 편집 중 차량 카드를 2초 누르면 기존 구성 메뉴에 차량 이동을 표시. 선택 시 지도 편집을 종료하고 기존 목적지 선택/맞바꾸기 확인 절차를 재사용한다.
- 새 주문부터 업체 또는 개인 주문자를 반드시 선택·등록한다. 기존 주문에 임의의 고객을 소급 연결하지 않는다.
- 최초 admin과 admin이 허용한 활성 관리자만 고객 등록·검색·조회·신규 주문 배정 가능. 작업자는 기존 주문의 장착/출고·차량 이동 권한을 유지한다.
- 업체명 자동완성은 입력 문자열의 앞부분으로 검색하고 20개씩 조회한다. 선택하면 기존 고객 ID를 재사용한다. 동일한 이름을 새로 등록하는 경우 별도 고객으로 유지한다.
- 고객별 출고 기록은 50개씩 날짜 역순으로 조회한다. 기존 출고 목록/마감 스냅샷에는 이름 평문을 추가하지 않는다.
- 계정 생성/수정·비밀번호 재설정은 최초 관리자에게 한정했다. 다른 관리자가 최초 관리자 비밀번호를 재설정해 개인정보 권한을 획득할 수 없게 하기 위한 의도적인 권한 변경이다.
- 관리자 비활성화/역할 변경 시 고객정보 권한을 회수한다. 다시 활성화해도 최초 관리자가 새로 부여해야 한다.

## 데이터 연결
customers(안정적인 고객 ID, 구분, 암호화 이름)
→ order_customers(주문별 고객 ID와 암호화 이름 사본)
→ outbound_customers(실제 출고 ID, 주문 ID, 고객 ID, 출고 당시 암호화 이름)
→ vehicle_customer_events(차량·출고와 고객의 관계 이벤트)

차량 ID, VIN, Stay, Order, Outbound는 기존 식별자를 유지한다. 새 기록은 별도 테이블로 추가한다.
고객/주문 연결/출고 연결/고객 감사 이력/차량 고객 이벤트는 UPDATE/DELETE 차단 대상으로 등록했다.
권한 변경과 고객정보 접근은 사용자 ID·시각·이벤트·대상 ID만 기록하고 이름·검색어는 감사 로그에 쓰지 않는다.
고객 검색은 비밀키를 사용하는 HMAC 접두어 인덱스로 처리한다. 요청마다 전체 고객명을 복호화하지 않는다.

## 승계 및 향후 금융 영역
vehicle_customer_events는 DELIVERY/TRANSFER 유형, 이전 고객 ID, 새 고객 ID, 이전 이벤트 ID, 효력일, 처리자, 암호화 사유를 수용한다.
현재는 고객이 연결된 실제 출고 시 DELIVERY 이벤트만 생성한다. TRANSFER 확정 API·화면은 구현하지 않았다.
승계 확정은 추후 동일 차량/이전 관계 유효성, 중복 요청, 효력일, 승인자 검증을 포함해야 한다. 최초 출고 고객은 수정하지 않는다.
계약은 독립 계약 ID로 고객 관계와 연결한다. 보험증서·계약서 파일도 별도 암호화 저장·접근 기록·보존 기준이 필요하다.
리스/렌탈의 일·월 사용료는 적용 기간별 계약 조건 버전으로, 청구·입금·배분·미수는 별도 원장으로 관리할 예정이다.
승계가 과거 미수/채무/기존 계약을 자동으로 새 고객에게 이전해서는 안 된다. 승계 효력일과 금융 이전 범위는 별도 확정해야 한다.
계좌 연결, 입금 동기화, 미수 알림, 보험·계약 문서 입력, 고객 병합·이름 정정은 이번 구현에 포함하지 않는다.

## 암호화와 보호 범위
- 이름: cryptography Fernet 인증 암호화. 검색 토큰: 도메인 구분한 HMAC-SHA256. 암호문과 접두어 토큰은 DB에, 키는 DB/Git 밖에 저장한다.
- 접두어 토큰에는 평문이 없지만 같은 접두어의 일치 관계 등 일부 검색 패턴은 드러난다.
- 권한 검사를 모든 고객 API와 신규 주문 처리 서버에서 실행한다. 이름은 공용 /state·출고 스냅샷·localStorage/sessionStorage에 포함하지 않는다. 브라우저의 명령 재시도에는 고객 ID만 남긴다.
- 브라우저 입력·표시 중 메모리, 허용된 관리자가 보는 화면, 서버 프로세스의 복호화 메모리는 암호화 저장 보호와 별개다. 서버 OS 관리자/키 파일 접근자까지 차단하는 시스템은 아니다.
- 기존 구매입고 자료의 계약자명, 일반 메모·과거 가져오기 원본까지 자동 암호화한 것은 아니다. 이를 같은 개인정보 영역으로 확장하려면 별도 데이터 분류·마이그레이션이 필요하다.
- 네트워크는 기존 HTTPS/Tailscale 연결을 사용해야 한다.

## 키 설정·복구 (운영 적용 전 필요)
기본 키 위치: %LOCALAPPDATA%\ScooterWarehouse\keys\customer.key.
서버 계정으로 실행하며 필요하면 WAREHOUSE_CUSTOMER_KEY_FILE 절대 경로로 지정한다. 키 내용/비밀번호를 채팅이나 Git에 넣지 않는다.

```powershell
# 배포할 커밋의 소스에서 실행. 운영 DB 경로는 실제 사용하는 경로로 확인한다.
python -m server.customer_keys init --database "실제운영DB경로" --file "별도보관위치\customer.keybackup"
```

이 명령은 터미널에서 복구 비밀번호를 두 번 입력받는다. 키와 백업 파일은 기존 파일을 덮어쓰지 않고, Windows에서는 현재 사용자와 SYSTEM만 접근하도록 ACL을 제한한다.
고객 데이터가 존재하는데 키가 없으면 새 키 생성은 거부한다. 키 분실 시 DB 백업만으로 고객명을 복구할 수 없다.
DB 전체 백업에는 암호문이 포함되지만 원본 키는 포함하지 않는다. 비밀번호로 암호화한 .keybackup을 별도로 보관한다.

```powershell
python -m server.customer_keys backup --file "별도보관위치\customer-추가백업.keybackup"
python -m server.customer_keys restore --database "복원대상DB경로" --file "별도보관위치\customer.keybackup"
```

복구는 DB의 기존 암호문으로 키 일치 여부를 확인하고, 기존 키 파일이 있으면 중단한다. 키 회전은 아직 제공하지 않는다.

## 실행한 검증
- pytest 54개: 고객 권한, 암호화/잘못된 키, 자동완성/페이지, 키 암호화 백업·복구, 필수 입력, 출고 연결, 기존 업무/사진/재고/스냅샷 보존, OCR 제거 검사 통과.
- 실제 Chromium: 지도 편집 2초 누르기, 차량 이동 메뉴, 편집 종료, 고객 자동완성·선택, 브라우저 영구 저장소에 이름 없음 검사 통과.
- 기존 Android VIN 기본 카메라 경로 회귀 브라우저 검사 통과. 실제 갤럭시 터치·기본 카메라 검증은 미실행.
- 실제 운영 계정·기존 업무 데이터에 새 구조 적용, 운영 키 생성·복구 훈련은 아직 실행하지 않았다.

## 배포·복구
운영 커밋/작업트리가 기준과 일치하는지 확인하고 DB·사진 백업 및 키 백업을 준비한 뒤 fast-forward로 적용한다.
DB 변경은 새 테이블·인덱스·불변 트리거 추가이며 기존 출고/마감/부품 기록을 다시 쓰지 않는다.
키 설정과 최초 admin 식별이 확인되기 전 운영 신규 주문을 차단시키는 배포를 하지 않는다.
코드 복구 시 고객 기록이 이미 생겼다면 이전 코드로 단순 복귀하여 이름 없는 새 주문이 만들어지지 않도록 주문 등록을 중지한 상태에서 대응한다. DB를 과거 백업으로 덮어쓰지 않는다.
